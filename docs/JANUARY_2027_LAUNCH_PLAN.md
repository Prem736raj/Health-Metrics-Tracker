# Health Metrics Tracker launch plan for January 1, 2027

**Decision:** Relaunch in India as a private personal health record for adults. Start with one job a person can finish end to end: record home blood pressure or weight, correct a mistake, see what changed, and take a readable report to a visit. Keep the existing water, food and calculator tools accessible. The next additions should make a person's history more complete or easier to use.

**Dates:** November 21, 2026 through January 1, 2027, India time. Target submission by December 18. January 1 is the public availability target, subject to review and verification. The 9/10 target is an engineering and product review score. Store ratings, installs and retention must come from real users.

## Starting evidence

- The November review scored the app **5.9/10**. The audited source matches master `83191f1`. Its Android CI passed 26 API 34 instrumented tests. The static detail palette check passed 1,496 combinations. Neither result measures a person's ability to log a reading or recover their history.
- Play Console showed **Health Metrics Tracker: BMI**, package `com.healthmetrics.tracker`, unpublished, with an earlier production rollout in India. The uploaded 1.0.3 bundle has code 4 and predates the November fixes. Internal testing was on code 2. Retain the package and signing identity. Allocate the next unused code for every new bundle and promote the tested artifact across tracks.
- The last observed 28-day Play view had 15 device impressions, one acquisition and one first open. Seven-day retention was unavailable. Treat the launch as a new demand test. The original eight store screenshots lead with Home and Water.
- The listing describes Gemini and optional analytics. The hosted policy names Analytics alone and the Console Data safety summary says no collection or sharing. The app-level trader declaration needs attention. Verify against the candidate bundle and actual provider settings.
- Market reference points from the November review: Samsung Health offers broad device integration, Appovo a quick BMI result, Libra a dedicated weight diary, and SmartBP cuff import and reports. Test whether **fast manual entry, no required account, explicit missing days, portable history and one visit report** together win a specific audience. Download bands do not establish demand for this product. ## The January experience

| Journey | Product decision | Observable result |
|---|---|---|
| First minute | Let an adult choose BP, weight, or explore. Open a focused entry form, allow profile setup later, and explain that BP comes from the user's monitor. | A new user can save a reading offline without creating an account, granting a health permission or finding a calculator first. |
| Daily use | Put the preferred action and last saved reading on Today. Expose add, edit and delete with undo or explicit confirmation. Keep source, units and measurement time visible. Offer a widget shortcut and optional reminder after the first successful save. | Repeat entry is quick. Switching units, going back, rotating, or tapping twice does not create a second record. |
| Find a record | Provide a chronological BP and weight history using existing data. Filter by type and date; show a plain-language source such as Manual or Health Connect. A note belongs to its reading. | Yesterday's corrected weight appears once everywhere. Two genuinely different observations with the same value are retained. |
| Prepare for a visit | Build on the existing report/export screens. Offer a 7- or 30-day summary, dates, units, counts, days with observations and an optional dated table. Preview selected sections before exporting a PDF. Keep raw CSV available. | The on-screen and exported values match. Users can tell what was recorded, what was missing and what they chose to share. |
| Keep the history | Add a user-controlled, versioned backup and restore of explicitly listed record types. Explain coverage and protect the backup with established authenticated encryption and a user-held recovery secret suitable for transfer to a new device. | A fresh installation restores dates, units, notes, stable IDs and provenance. Wrong password, damaged archive, duplicate import or interruption preserves existing data. |

**First-release scope choices.** Keep weight and BP as the two complete journeys. Put specialized calculators behind Tools. Replace generic Wellness Score prominence with a literal count or last check-in. Deprioritize milestones, new streaks, additional calculators and more botanical variants. Recommend keeping the generative assistant out of the launch's primary navigation and marketing. Decide by November 25 whether to retain it as a secondary opt-in or disable it throughout this release. If disabled, remove reachable entry routes and align the SDK paths and listing. Historical conversations still need an accessible deletion path. Using AI to build the app is independent of offering AI chat to users.

## How to build it with AI

Use one coding chat per ticket and a branch based on current GitHub master. Keep large changes such as restore separate from navigation. Give the coding agent the exact issue, this plan, existing entry points and the expected user-visible behavior. Have it inspect the callers, persistence and tests before editing. Require a diff, executable verification, remaining uncertainties and a short reviewer walkthrough. Give a fresh reviewer the ticket, candidate diff and acceptance criteria to look for regressions. Merge only after required checks pass.

**Reusable build prompt**

> Implement ticket [ID] from docs/JANUARY_2027_LAUNCH_PLAN.md on the current integration branch. Trace the real UI entry, repositories and existing data model first. Use synthetic fixtures. Reuse the current storage and navigation where possible. Exercise the happy path plus the failure and upgrade cases listed in the ticket. Report changed files, actual test output, device or emulator coverage, and which acceptance criteria remain open. Keep changes scoped to this ticket.

**Reusable review prompt**

> Review [ID] from the perspective of a returning user upgrading from code 4 and a new offline user. Check persistence, units, missing data, duplicate saves, consent, accessibility and back navigation where applicable. Identify reproducible issues by severity with file locations. Distinguish what was executed from what was inferred.

AI can implement screens, migrations, report layouts, tests, release notes, localization drafts and candidate store assets. The owner verifies the actual organization’s trader and privacy answers, signing identity and publication action. A qualified reviewer assesses health terminology. Test participants establish whether the product is understandable. Never use someone’s real medical record in prompts, analytics, issue attachments or store art.

## Growth experiments for India

1. **Discover the job.** Recruit 10 adults already using a notebook, spreadsheet or another tracker through opt-in personal or community channels. Ask them to show how they prepare for a visit using a fictional example. Learn what they need to retrieve and which existing habit the app must beat. Invite a second group of 10 for the pilot. Avoid collecting diagnoses or copies of reports for recruitment.
2. **Show the result in the listing.** Test the current BMI-led title against **Health Records: BP & Weight**. Example short description: “Log blood pressure and weight, see trends, and share a clear visit report.” The first three screenshots should show a saved reading, a dated timeline and a readable report. Use invented records. Keep calculators and water farther down. Offer one short demo through the existing support or project site.
3. **Give users a reason to return.** After a successful save, offer a preferred metric and an optional reminder at a user-chosen time. After enough readings, show the first useful comparison and the underlying dates. Let users preview and share a report by deliberate action. Avoid exposing health details on lock screens or adding promotional content to medical reports.
4. **Measure the right loss.** Start with raw counts: eligible listing visitors → acquisitions; first opens → first saved record; first savers → another save on a different day; eligible first savers → return in days 7–13; report previews → successful exports. State the window, denominator and consent coverage. Use Play aggregates, voluntary pilot observation or existing consented coarse product events. Keep values, free text, attachments and diagnoses out of telemetry.
5. **Decide with evidence.** For the initial 20-person pilot, target 16 first saves and 8 people who log on another day within a week. These are decision thresholds, not forecasts. With one historic acquisition, organic A/B conversion results will be unstable. Use qualitative listing tests first, then a Play listing experiment once traffic is sufficient. Hold paid promotion until repeat use and support workload are understood.

## The 9 out of 10 review

Use the same weights as the original review. For each row award 2 points for each demonstrated item, 1 for partial evidence, and 0 for unavailable or failed evidence. Capture the numerator, denominator, test build, dates and reviewer. The weighted total must reach 9.0/10; label prelaunch and postlaunch evidence separately. An unresolved safety, privacy, data-loss or core accessibility blocker is a no-go regardless of score.

| Area | Weight | Five pieces of evidence |
|---|---:|---|
| Recurring usefulness | 25% | First-save pilot target met; repeat-save target met; at least 8/10 people locate a past record unaided; at least 8/10 explain a sample report accurately; interviewees can name a recurring use beyond a one-time calculator. |
| UX and accessibility | 20% | 9/10 record a first BP or weight within 60 seconds unaided; 9/10 correct an entry; full flow works with TalkBack; full flow works at 200% text in both themes; empty, offline and denied states each give a usable next action. |
| Reliability and accuracy | 20% | Upgrade preserves data; duplicate/partial writes handled; sparse data and units correct; report matches fixtures; backup restore and failure cases pass. |
| Privacy and health trust | 20% | Candidate data map reconciled with policy/Console; opt-ins and revocation exercised; medical content reviewed; deliberate export/deletion tested; Play and Health Connect disclosures verified on device. |
| Engineering and verification | 15% | Candidate passes CI; release-like testing across supported API boundaries; median actionable Home within 2 seconds over 10 cold launches on the named test phone; 12-month history responsive during entry/edit/export with benchmark recorded; release recovery and support rehearsal completed. |

## After January 1

| Horizon | Expansion toward a complete record | Condition for proceeding |
|---|---|---|
| **January** | Add visit notes, provider/date search and a local attachment folder for lab PDFs or prescription images. Link a file to a visit, preview before sharing, include it in backup, and allow permanent deletion. | Pilot users repeatedly need records that the January report cannot capture. Validate file type/size, storage limits, private previews, deletion and archive portability with synthetic files first. |
| **February** | Add a medication list as entered by the user, lab values with units and lab-supplied reference intervals, and optional BP import through Health Connect. | Identity, units, provenance, corrections and duplicate handling work for each new record type. Ask only for the specific permission required by a selected feature. |
| **Later** | Evaluate caregiver profiles, device partnerships, or interoperable exports when there is a named workflow and partner. Family members' records must be isolated across history, reports, backups, widgets and notifications before enabling multi-profile use. |
